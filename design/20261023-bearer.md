# Server-side `Bearer` challenges and credentials

Date: 2026-10-23

# Problem statement

A resource server accepting OAuth 2.0 access tokens sends `Bearer` challenges
([RFC 6750 section 3](https://datatracker.ietf.org/doc/html/rfc6750#section-3)),
optionally pointing to its metadata with `resource_metadata`
([RFC 9728 section 5.1](https://datatracker.ietf.org/doc/html/rfc9728#section-5.1)),
and reads the token from `Authorization: Bearer <token>`
([RFC 6750 section 2.1](https://datatracker.ietf.org/doc/html/rfc6750#section-2.1)).

Non-goals: token validation, metadata documents, grants, form-encoded or
query-string tokens.

# Decision outcome

Module `bearer`, behind `server`; no new dependencies.

*   `bearer::ChallengeBuilder::new()` with optional `realm`, `scope`,
    `error`, `error_description`, `error_uri`, `resource_metadata`; `build()`
    returns a `Challenge`, written in that order.
*   `bearer::ErrorCode`: `InvalidRequest` (400), `InvalidToken` (401),
    `InsufficientScope` (403), via `status()`.
*   `bearer::Credentials::parse(source)` returns the `token68`, like
    `basic::Credentials::parse`.

## Validation rules

| Rule | Error |
|---|---|
| `realm` quotable | `ConfigError` |
| `scope`: `scope-token`s (`%x21 / %x23-5B / %x5D-7E`) separated by single spaces | `ConfigError` |
| `error_description`, `error_uri`, `resource_metadata`: `%x20-21 / %x23-5B / %x5D-7E` | `ConfigError` |
| Credentials: body is a `token68` | `ServerError::Malformed` |

# Testing

*   RFC 6750 section 3 and RFC 9728 section 5.1 examples.
*   Every challenge parameter parsed back with `parse_challenges`.
*   One negative test per validation rule.
